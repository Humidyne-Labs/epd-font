# Legacy Bilevel Font Conversion Methodology Summary (`epd-font` v1.0.17)

- **Repository**: [Humidyne-Labs/epd-font](https://github.com/Humidyne-Labs/epd-font) (`repo_tag_value = v1.0.17`)
- **Project Description**: A 1-bit EPD font generator and asset pipeline for embedded displays
- **Lead Designer & Developer**: [Humiditron](https://github.com/humiditron) (Humidyne Labs) & AI/LLM Collaborative Development Partner
- **Document Scope**: Formal archival summary of the `v1.0.17` bilevel (`1-bpp`) font conversion methodology prior to the `v1.0.18` multi-pipeline architectural pivot.

## 1. Multi-Core Static TrueType (`.ttf`) Synthesis & Anisotropic Variable Extrapolation

In `epd-font` `v1.0.17` ([Humidyne-Labs/epd-font](https://github.com/Humidyne-Labs/epd-font)), the upstream asset preparation subsystem (`tools/fonts/build_static_ttf_assets.py`) transforms heterogeneous raw typography and iconography packages stored in `assets/` into a standardized repository of `113` static TrueType (`.ttf`) binaries inside `build/static_ttfs/`. Rather than modifying raw source archives in place, the builder indexes Variable TrueType masters ([IBM Plex](https://github.com/IBM/plex)), hinted static cuts ([Google Noto](https://github.com/notofonts/latin-greek-cyrillic)), OpenType Compact Font Format (`.otf`) icon suites ([Font Awesome 7](https://fontawesome.com/), [Lucide Icons](https://lucide.dev/), [Phosphor Icons](https://phosphoricons.com/), and [Tabler Icons](https://tabler.io/icons)), and X11 Bitmap Distribution Format (`.bdf`) console strikes ([Terminus Font](https://terminus-font.sourceforge.net/)). Using Python's `ProcessPoolExecutor` across all available host CPU cores, the asset builder instantiates static font cuts, converts cubic Bézier PostScript curves (`CFF`) to quadratic TrueType (`glyf`) contours via `cu2qu`, and compiles searchable JSON metadata catalogs (`build/metadata/*.json`) alongside SHA-256 integrity digests.

A central mathematical mechanism of the `v1.0.17` static asset builder is its anisotropic `gvar` delta extrapolation for synthesizing `ExtraBold` (`wght = 800`) cuts from IBM Plex Variable masters whose native weight axis terminates at `Bold` (`wght = 700`). On a `188.3 DPI` (`200x200` pixel) `1-bpp` monochrome electrophoretic display (EPD), standard `Medium` (`wght = 500`) and `Bold` (`wght = 700`) stems both quantize toward `2 px` integer runs at `12 px` to `16 px`, diminishing visual weight hierarchy. To establish a `3 px` bold stem width without closing internal glyph apertures, `v1.0.17` extrapolated positive-weight `gvar` coordinate deltas anisotropically—scaling horizontal stem displacements by `1.45x` while constraining vertical bar displacements to `1.18x`.

For low-resolution terminal readouts (`12 px` to `32 px`) and integer-doubled display sizes (`36 px` and `40 px`), `v1.0.17` also converted `20` native Terminus `.bdf` bitmap strikes into `24` individual quadratic TrueType outline files (`Terminus-Normal-<sz>.ttf`, `Terminus-Bold-<sz>.ttf`, and `Terminus-VGA-<sz>.ttf`). Each active bitmap pixel run on scanline $y$ spanning columns $[x_0, x_1)$ was mapped into a clockwise rectangular contour on an exact `UPEM = 1024` coordinate lattice (`64` font units per pixel), allowing bitmap console fonts and continuous outline fonts to flow through a single FreeType 2 ingestion interface.

## 2. FreeType 2 Scanline Rasterization & Adaptive Otsu/Topology Thresholding

The primary `v1.0.17` rasterization subsystem (`tools/fonts/humid1_ft_raster.py`) interfaces directly with the host `libfreetype` shared library via Python `ctypes` bindings (`FT_Library`, `FT_FaceRec`, `FT_GlyphSlotRec`, and `FT_Bitmap`). For each requested pixel height (`ppem`) and Unicode codepoint set defined in a declarative `.scheme.json` file, the module configures pixel dimensions via `FT_Set_Pixel_Sizes()`, extracts horizontal advance widths (`hmtx`) in `1/16th` pixel fixed-point units (`FP4`), and parses both legacy TrueType `kern` tables and OpenType `GPOS` Pair Adjustment (`LookupType 2` Format 1 and Format 2 class-based) subtables. Sub-pixel kerning pairs whose `FP4` adjustment does not change the rounded integer advance width are pruned automatically to conserve microcontroller read-only memory (`.rodata`).

To convert continuous vector outlines into `1-bpp` binary pixel matrices, `v1.0.17` relied primarily on the `autohint-mono` rasterization mode (`FT_LOAD_RENDER | FT_LOAD_FORCE_AUTOHINT | FT_LOAD_TARGET_NORMAL` for sizes $\le 20	ext{ px}$). Instead of invoking FreeType's legacy `1-bit` monochrome scanline dropout converter (`FT_LOAD_TARGET_MONO`), which frequently introduces diagonal stair-step spurs ([FreeType 2 Subpixel Hinting Notes](http://freetype.org/freetype2/docs/hinting/subpixel-hinting.html)), `v1.0.17` rendered glyphs into an `8-bit` grayscale coverage buffer (`256` levels) with symmetric Latin stem grid-fitting and then applied a coverage threshold to binarize each pixel into active ink (`#`) or background (`.`). For native Terminus bitmap strikes, the pipeline switched to `exact-mono` (`FT_LOAD_RENDER | FT_LOAD_NO_HINTING | FT_LOAD_TARGET_MONO | FT_LOAD_MONOCHROME`) to preserve bit-exact integer coordinates.

When configured for dynamic thresholding (`--threshold 0` or `--raster-mode dynamic-threshold`), `v1.0.17` replaced the fixed midpoint threshold ($T = 128$) with an adaptive threshold estimator (`compute_dynamic_threshold()`). This function combined a weight-and-size prior $T_{	ext{prior}} \in [92, 160]$ with a 1D Otsu between-class variance maximization over active edge pixels ($I(x,y) > 16$), and then evaluated candidate offsets $\Delta T \in \{-12, -6, 0, +6, +12\}$ against horizontal run-length survival ($\ge 2	ext{ px}$) and interior background pocket counts on enclosed-aperture characters (`0, 4, 6, 8, 9, A, B, D, O, P, Q, R, a, b, d, e, g, o, p, q, %`).

## 3. Legacy Closed-Loop Algorithmic Auto-Tuner & 8x Reference IoU Gate (Retired in v1.0.18)

In `v1.0.17`, unpatched text glyphs underwent an automated post-rasterization modification pass implemented in `tools/fonts/humid1_bilevel_tuner.py` (invoked via `--workflow repair` and `08_iterative_auto_repair.bat`). The auto-tuner attempted to enforce a minimum `2 px` stem thickness floor (`min_stem_px = 2`) and open enclosed glyph counters at small pixel sizes (`10 px` to `16 px`) by comparing each low-resolution `1-bpp` bitmap against an unhinted `8x` high-resolution grayscale reference image rendered by FreeType (`FT_LOAD_NO_HINTING | FT_LOAD_TARGET_NORMAL`). Each `1-bpp` candidate was upscaled by `8x` via nearest-neighbor interpolation into the coordinate space of the continuous `8x` reference to compute structural Intersection-over-Union (`hq_conf_iou`), pixel mismatch percentage (`hq_diff_pct`), valley occlusion ratio (`valley_occ_pct`), and ink mass deviation (`mass_err_pct`).

The `v1.0.17` auto-tuner executed a multi-stage sequence of morphological and topological operators (`Stage 0` 4-directional isolated spur removal, `Stage 0b` interior aperture expansion and `1 px` bowl-join bridge sealing using 4-connected Euler-Poincaré Betti number $eta_1$ hole counting, `Stage 1` dual-hysteresis `8x` area downscaling, `Stage 2` collinear stem widening, and `Stage 3` central vertical spine duplication on `$`, `+`, `±` plus bilateral mirror-pair synchronization across `(` / `)`, `[` / `]`, `{` / `}`, and `<` / `>`). To prevent diagonal valleys in multi-stroke characters (`W, w, M, m, N, X`) from merging into solid blocks, the auto-tuner enforced a scanline run-count invariance constraint derived from the Pigeonhole Principle ($k \cdot w_{	ext{stem}} + (k - 1) \le W_{	ext{box}}$).

Despite these mathematical constraints, empirical visual inspection of `v1.0.17` outputs demonstrated that automated post-rasterization pixel mutation introduced unintended weight shifts, altered typeface character across adjacent sizes, and populated `font_icon_epd_patches.json` with `1,073` synthetic overrides that obscured true human-authored pixel edits. Consequently, per the `v1.0.18` architectural specification, the automatic tuner is permanently retired in `v1.0.18` in favor of four clean, deterministic primary conversion pipelines (`svg-potrace`, `raw-unhinted`, `raw-hinted`, and `mdf`) paired with strictly user-controlled manual ASCII patching.

## 4. Full-Canvas 1:1 Spaced ASCII Patch Pipeline & Declarative JSON Patch Manifest

To support deterministic pixel-level refinement without binary font editors, `v1.0.17` introduced the Full-Canvas `1:1` Spaced ASCII Patch subsystem (`tools/fonts/humid1_ascii_patches.py`). Running `--workflow patch --dump` (`04_dump_ascii_patches.bat`) exports every glyph in a strike to an individual human-readable text file (`build/<workflow>/ascii_patches/<strike_symbol>/U+<HEX>_<name>.txt`). Rather than cropping the exported grid tightly to the ink bounding box—which obscures vertical alignment for punctuation such as underscores (`_`), hyphens (`-`), periods (`.`), and apostrophes (`'`)—the dumper plots each glyph across its complete typographic cell canvas from the font ascender ($y = +	ext{ascent}$) down to the descender ($y = -	ext{descent}$) and across its full horizontal advance width.

Inside each `.txt` file, the YAML-style metadata header records the strike metrics (`adv_w_fp4`, `box_w`, `box_h`, `ofs_x`, `ofs_y`), the baseline-relative coordinate bounds (`canvas_x0`, `canvas_y_top`, `canvas_y_bot`), and a deterministic `orig_signature` string encoding the unmodified raster state. Below the `---` delimiter, the editable matrix renders each pixel using two monospace characters (`# ` for active ink, `. ` for empty canvas, and `- ` along the $y = 0$ baseline) so that standard text editors display the glyph at a true `1:1` square aspect ratio alongside right-hand landmark annotations (`ASCENDER`, `CAP_HEIGHT`, `X_HEIGHT`, `BASELINE (y=0)`, and `DESCENDER`).

When a developer modifies any `#` or `.` token in the ASCII grid and runs `--workflow patch --apply` (`05_apply_ascii_patches.bat`), `parse_ascii_glyph_folder()` scans all `U+*.txt` files, compares the current bitmap signature against `orig_signature`, and automatically recalculates the tight bounding box (`box_w`, `box_h`, `ofs_x`, `ofs_y`) relative to the origin $(0,0)$. Modified glyphs are compiled into the root-tracked `font_icon_epd_patches.json` manifest, which is subsequently ingested during static asset and C/H font generation to form a closed-loop manual editing workflow.

## 5. Tri-Role Visual Contrast Triad Evaluation & Size-Floor Benchmarking

The `v1.0.17` evaluation subsystem (`tools/fonts/humid1_font_eval.py`) benchmarks candidate typefaces across multiple pixel sizes (`10 px` to `24 px`) to determine each font's viable pixel size floor and optical role suitability on `1-bpp` displays ([A Closer Look at Font Rendering](https://www.smashingmagazine.com/2012/04/a-closer-look-at-font-rendering/)). Earlier revisions (`v1.0.15`) scored fonts in isolation by maximizing `8x` reference IoU confidence, which inadvertently favored `SemiBold` (`w600`) for normal body text (`2.36 px` stem) and `Bold` (`w700`, `2.57 px` stem) for bold text—leaving only a `+6.5%` ink mass difference between normal and bold while selecting `ExtraBoldItalic` (`w800`, `3.08 px` stem) that appeared heavier than bold.

To resolve this optical homogeneity, `v1.0.17` implemented the Tri-Role Visual Contrast Triad Scorer (`evaluate_family_triads()`). Rather than grading cuts in isolation, the evaluator groups cuts by typeface sub-family (preserving `Normal`, `SemiCondensed`, `Condensed`, and `ExtraCondensed` width tiers) and evaluates complete `(Normal Body + Bold Emphasis + Subtle Iso-Weight Italic)` triads. A high-scoring triad requires the `Normal` cut (`w400–w500`) to sit cleanly on a `2.00 px–2.25 px` stem grid with `100%` open internal counters, the `Bold` cut (`w800–w900`) to deliver a `+35%` to `+65%` ink mass gain and a `+0.85 px` to `+1.45 px` integer stem step (`2 px -> 3 px`), and the `Italic` cut (`w500–w600`) to remain within `[-10%, +12%]` of normal ink mass and at least `25%` lighter than bold.

For every evaluated font and family triad, `humid1_font_eval.py` generates per-font visual inspection sheets (`build/font_eval/sheets/<font>_eval.png`), paginated full-corpus comparison scorecards (`font_eval_comparison_sheet.png`), and stacked triad contrast sheets (`font_eval_triad_contrast_sheet.png`) alongside structured Markdown, CSV, and JSON reports.

## 6. LVGL v8/v9 C/H Source Emission, Adobe BDF 2.1 Export & Zero-Dependency Strike Vault

The final stage of the `v1.0.17` pipeline (`tools/fonts/humid1_lvgl_bdf_export.py` and `tools/fonts/humid1_fw_emit.py`) translates rasterized and patched `GlyphStrike` objects into embedded C source modules (`.c`), C/C++ header files (`humid1_fonts.h`, `epd_fonts.h`, `plex_fonts.h`, `h1os_fonts.h`), Adobe BDF 2.1 archival bitmap fonts (`build/<workflow>/bdf/*.bdf`), per-strike character width and kerning CSV tables (`build/<workflow>/metrics/*.csv`), and visual diagnostic blueprints (`tools/fonts/humid1_visual_check.py`). Each LVGL `.c` module packs `1-bpp` glyph bitmaps MSB-first (`bpp = 1`, `bitmap_format = 0`), partitions Unicode codepoints into contiguous `LV_FONT_FMT_TXT_CMAP_FORMAT0_TINY` and sparse `LV_FONT_FMT_TXT_CMAP_SPARSE_TINY` subtables, and emits `lv_font_fmt_txt_dsc_t` and `lv_font_t` descriptors.

To decouple embedded firmware compilation (such as ESP-IDF CMake builds on `ESP32-S3`) from host C libraries (`libfreetype`, `OpenCV`, or `fonttools`), `humid1_generate_1bpp.py` serializes all pre-rasterized strikes, kerning arrays, and metrics into a compressed JSON archive (`humid1_epd_vault.json.gz`, the Strike Vault). During firmware compilation, the lightweight `humid1_fw_emit.py` script—written strictly in the Python 3 standard library (`json`, `gzip`, `pathlib`, `argparse`)—reads the Strike Vault, applies any local ASCII `.txt` glyph overrides, filters glyphs to the active `.scheme.json` character sets, and emits `.c`/`.h` sources in under `0.15` seconds.

Alongside the C sources, the exporter writes `total_disk_size.txt`, tabulating per-strike and per-family `.rodata` Flash memory footprints (`glyph_bitmap` + `glyph_dsc` + `cmaps` + `kern_pairs`) and auditing horizontal string pixel lengths (`run_screen_width_audit()`) against the target display's safe horizontal pixel budget (`188 px` on a `200x200` panel with `6 px` margins).
