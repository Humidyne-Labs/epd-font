## 1. Executive Summary & Pre-Audit Scope

Prior to implementing the `v1.0.18` architectural pivot specified in `humid1-audit-v1.0.18.md`, a comprehensive static, structural, and functional pre-audit was conducted across the `epd-font-v1.0.17-fixme.zip` baseline (`14` Python modules totaling `11,215` lines of code, `32` Windows `.bat` launchers, `20` declarative `.scheme.json` files, and `113` static `.ttf` assets). The pre-audit evaluated compliance against the `v1.0.18` requirements, the mandatory Lexicon Rule, LVGL `>= 9.6.0` compatibility, multi-pipeline conversion capabilities ([Potrace Vector Tracing](https://potrace.sourceforge.net/), [FreeType Hinting](http://freetype.org/freetype2/docs/hinting/subpixel-hinting.html), [Multi-Channel / Signed Distance Fields](https://github.com/Chlumsky/msdfgen), and [Red Blob Games SDF Typography](https://www.redblobgames.com/articles/sdf-fonts/)), CLI/path validation, and embedded ROM budget estimation.

## 3. Detailed Pre-Audit Analysis by Subsystem

### 3.1 Bilevel Rasterization & Pipeline Architecture (`humid1_ft_raster.py` & `humid1_bilevel_tuner.py`)
In `v1.0.17`, `rasterize_font_strike()` supports only direct FreeType rasterization (`FT_LOAD_FORCE_AUTOHINT` or `FT_LOAD_NO_AUTOHINT`) followed by grayscale thresholding (`threshold = 128` or Otsu dynamic thresholding). As documented in `docs/audits/notes/potrace.md` and `docs/audits/notes/potrace_alt.md`, direct low-resolution rasterization depends heavily on internal font hints; when hints are absent or sub-optimally grid-fitted at `10 px` to `18 px`, stems exhibit uneven pixel widths and aliasing stair-steps ([How the stb_truetype Anti-Aliased Software Rasterizer Works](http://nothings.org/gamedev/rasterize/)). Introducing the four selectable conversion pipelines (`raw-unhinted`, `raw-hinted`, `svg-potrace`, and `mdf`) allows side-by-side empirical evaluation across every typeface and pixel size without relying on destructive post-rasterization auto-tuning.

### 3.2 LVGL `>= 9.6.0` Descriptor & Fallback Chain Integrity (`humid1_lvgl_bdf_export.py` & `humid1_fw_emit.py`)
Inspection of `emit_lvgl_c_file()` in both `humid1_lvgl_bdf_export.py` (lines `300–355`) and `humid1_fw_emit.py` (lines `358–410`) confirmed that while `.fallback` is emitted inside `#if LV_VERSION_CHECK(8, 2, 0) || LVGL_VERSION_MAJOR >= 9`, `humid1_fw_emit.py` did not prefix or resolve fallback symbol names against the active scheme's emitted symbol table. In LVGL `>= 9.6.0`, every `lv_font_t` descriptor requires `.fallback` to point either to `NULL` or to a valid, externally declared `const lv_font_t` symbol compiled into the same firmware image, with zero cyclic references.

### 3.3 CLI Validation, Signal Handling, and Build Directory Hierarchy
In `v1.0.17`, invoking `python tools/fonts/humid1_generate_1bpp.py` with zero arguments silently assumed `<repo>/build/static_ttfs`, `<repo>/build`, and `humid1_reference.scheme.json`. Per Requirement `8` and Requirement `10.b`, all tools in `v1.0.18` must validate CLI arguments and scheme file paths explicitly, fail gracefully with clear guidance when required configurations are missing or invalid, and organize all intermediate outputs, evaluations, audits, and caches under a unified `build/` tree (`build/static_ttfs/`, `build/metadata/`, `build/cache/`, `build/evals/`, `build/audits/`, `build/<scheme>/`).
